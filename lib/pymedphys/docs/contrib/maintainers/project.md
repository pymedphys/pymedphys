# Maintain the project

For maintainers routing issues, supporting contributors and maintaining shared infrastructure. Responsibilities below describe the current work, and do not adopt pending appointment or support-policy proposals.

## Route incoming work

Use [Discussions](https://github.com/pymedphys/pymedphys/discussions) for help and open-ended questions, and [Issues](https://github.com/pymedphys/pymedphys/issues) for reproducible defects and scoped work. Ask for the version, environment, reproducible steps, expected result and synthetic or approved sample inputs. Follow [CONTRIBUTING](../index.md#keep-patient-data-out-of-public-posts) for public-data handling and the [security policy](https://github.com/pymedphys/pymedphys/blob/main/SECURITY.md) for private vulnerability reports.

For a contributor's first change, point to [First contribution](../start/first-contribution.md), agree a manageable scope and help interpret selected checks. Describe missing evidence or an unresolved decision explicitly rather than asking for undocumented requirements.

## Infrastructure responsibility

Repository maintainers administer rulesets, CI secrets and environments; Read the Docs project administrators manage hosted automation rules; release maintainers verify publishing access and record outcomes. Authoritative access is held in the services' settings. Do not infer access from an historical proposal or list of contributors.

Maintainers listed in the canonical README are Simon Biggs, Stuart Swerdloff, Matthew Jennings and Phillip Chlap. Coordinate a named owner for each substantial workstream through its tracking issue. The [documentation workstream register](../../project/documentation.md#ownership-and-update-triggers) identifies the documentation coordinator and subject-review responsibilities for this restructure. A subject reviewer checks the relevant scientific or vendor knowledge; access to a service alone does not establish that expertise.

## Track programmes and policy

Keep multi-PR programme decisions in [Design programmes](../design/index.md), each PR's scope and verification in its description, and progress in its tracking issue. Use [#1665](https://github.com/pymedphys/pymedphys/issues/1665) for documentation restructuring, [#1634](https://github.com/pymedphys/pymedphys/issues/1634) for tutorials and [#2140](https://github.com/pymedphys/pymedphys/issues/2140) for release-related gaps.

The [compatibility page](../../project/compatibility.md) separates confirmed rules from unresolved proposals. Recheck responsibilities when access, documented policy or maintainers change.
